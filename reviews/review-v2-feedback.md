## 二、锁定讲稿前必须修正（P0）

### P0-1：知识点映射表 K12 的采样顺序仍然写反

**位置：§3.2，K12（约第 575 行）。**

当前 K12 写成：

> logits→softmax→温度（T<1 尖锐/T>1 平坦/T→0 贪心）→Top-k/Top-p 截断归一化

这与 v2 自己的第 8 节讲稿、S24 分镜和 §3.6.3 的代码顺序约束冲突。

应统一为：

> logits → Temperature 缩放 logits → Softmax → Top-k / Top-p 截断 → 对保留候选重新归一化 → Sampling

**验收要求：** 搜索整份文档中的 `Softmax`、`Temperature`、`温度`，所有流程描述、知识映射、分镜、动画代码说明必须一致。不要只修正文案而遗漏表格。

### P0-2：第一集讲了 Attention 和 FFN，却漏掉 RoPE、Residual、Norm

**位置：§3.3 第 5 节 Prefill，尤其讲稿第 623–626 行；§3.4 S12–S13。**

原教程 Part II 第 3 章明确覆盖：
- 位置编码；RoPE 在 Attention 中对 Q/K 做旋转，使点积带有位置信息；
- Transformer Block 的 Attention + MLP/FFN；
- Pre-Norm、Residual、Norm；
- 多层堆叠及 final norm。

但 v2 当前旁白只讲“Attention 让 Token 之间通信”和“FFN 让每个 Token 自己消化”，然后直接说“两件事合起来是一层”。这容易让观众误以为真实 Block 只有 Attention 和 FFN 两个盒子。

**建议用 15–25 秒补足，不需要展开公式：**

1. 在进入 Attention 前插入位置编码/ RoPE：位置不是 Token ID 自带的；常见 RoPE 通过旋转 Q/K 注入位置信息。
2. 将 Block 画成 Pre-Norm → Attention → Residual Add → Pre-Norm → FFN/MLP → Residual Add。
3. 用一句话解释 Norm 稳定层输入分布，Residual 提供跨层直通路径。
4. 多层堆叠后再接 final norm 与 LM Head。

如果第一集确实要压缩，可以标注“本片只展示简化结构，Residual/Norm/RoPE 的细节在后续专集展开”，但不能把简化图当完整结构。

### P0-3：S12 的 Query 可见范围要写成“当前及之前”，包含自身

**位置：S12（约第 713 行）。**

目前写“最后一块的 Q 发出弧线连到前面 5 块的 K”。因果注意力中，位置 t 可以看到位置 1 到 t，包含当前位置自身，并非只看“前面”。

建议旁白和画面标注统一为：

> 当前 Token 的 Q，与当前位置及之前所有位置的 K 计算匹配分数；因果 Mask 屏蔽未来位置。

画面上将当前 Token 的 K 也纳入高亮，不要只画向左的历史连线。

### P0-4：“半个字节 / 左半字节”术语不准确

**位置：§2.3.2 的代码走读总结、S25（约第 741 行）。**

当前 S25 设计为“一个块只含‘缓’字左半字节”，这不是准确的技术描述。UTF-8 字符由一个或多个完整字节编码，Token 边界可能落在一个字符的字节序列中间；不存在“半个字节”这种需要表达的对象。

建议统一使用：

> 一个 Token 可能只包含某个 UTF-8 字符的部分字节序列。单独解码时，字节序列尚不完整，可能出现替代字符或不可显示内容。

动画应画成“一个汉字对应的多个 UTF-8 字节，被不同 Token 分段承载”，例如第一块携带前 1–2 个字节，下一块补齐剩余字节。避免画成“半个字节”或“汉字从中间物理切开”。

### P0-5：TTFT 的“首 Token”与用户看到的“首个可显示片段”需要分开

**位置：§3.3 第 5 节第 629 行、S16、K8。**

原教程 Benchmark 章节定义 TTFT 为请求发出到生成第一个 Token，包含排队与 Prefill；样片又增加了 Tokenizer、采样、Detokenizer 和首段返回的链路。

建议在同一时间轴上明确区分两个概念：

- **Benchmark TTFT（教程定义）：** 请求发出 → 第一个输出 Token 生成。教程强调包含排队与 Prefill，首 Token 由 Prefill 的前向计算直接产出。
- **客户端首段显示时间 / First visible chunk：** 请求发出 → 浏览器收到可显示文本。它还可能包含 Tokenizer、Detokenizer、网络与 SSE 刷新等开销。

不要把两者直接写成同一个指标。视频可以口语化讲“用户第一次看到内容的等待”，但指标角标应标明究竟采用哪种测量口径。

### P0-6：整集时长、逐节旁白时长和动画停顿三套数字对不上

**位置：§3.3 开头与各节时长标注（约第 584–681 行）。**

文档同时写了：
- 全文约 2530 字，按 4.2 字/秒，朗读约 10:00；
- 加动画停顿约 10:50；
- 十节区间总时长为 0:00–11:10；
- 各节标出的旁白时间之和为 494 秒（约 8:14）；
- 各节明确标出的纯动画停顿合计 76 秒；
- 旁白时间+明确停顿只有约 9:30，与 11:10 的分镜时间轴仍差约 100 秒。

个别章节也有明显差异，例如：
- Prefill 标注 3:10–5:40（150 秒），但旁白 95 秒+纯动画 15 秒，只解释了 110 秒；
- Detokenizer 标注 80 秒，但旁白 58 秒+纯动画 12 秒，只解释了 70 秒；
- 收尾标注 50 秒，旁白标注 42 秒，没有说明其余 8 秒用于什么。

**建议不要继续凭字数推算锁时间码。** 先把旁白稿放入实际 TTS 或人工录音，导出逐句时间戳；以音频时长为准重新分配镜头区间。纯动画停顿、转场、字幕停留单独标注。最后让 S01–S30 时间码连续、无空洞、无重叠，且总时长与成片长度一致。

## 三、建议同步修正的技术与制作问题（P1）

### P1-1：统一四站 / 五站的说法

**位置：§3.3 第 2 节（约第 595–600 行）与 S04（约第 695 行）。**

讲稿说“四个站点”，S04 又写“五站横向流水线”。原因是 API Server 同时负责接收请求和返回响应。

建议统一解释成：

> 四类逻辑组件：API Server、Tokenizer、Scheduler/Engine、Detokenizer。API Server 在请求入口和响应出口各出现一次，因此数据流图可以有五个路径节点，但不是五个独立服务。

这样同时避免“四站”和“五站”造成困惑，也能强调“逻辑分工不等于进程数量”。

### P1-2：`max_tokens` 与 `max_new_tokens` 的命名统一

**位置：K13（约第 576 行）、讲稿第 652 行、S23（约第 734 行）。**

不同章节可能使用不同字段名：概念说明里的 `max_new_tokens`、mini-SGLang `SamplingParams.max_tokens`、OpenAI 兼容请求里的 `max_tokens`。建议在第一次出现时给一条注释：

> 不同接口/实现中的字段名可能不同；本片按当前讲解对象使用对应名称，语义均指生成长度上限，具体以代码/API 定义为准。

不要在同一张图里混用而不解释。

### P1-3：S17 的 O(n²) 只限定“重复投影工作”，不要暗示整个 Attention 生成复杂度变成 O(n)

**位置：S17（约第 723 行）。**

无 KV Cache 时，历史 token 的 K/V 投影会在后续生成步中重复计算；跨生成步累加的这部分重复 K/V 投影工作可呈二次增长。

但使用 KV Cache 后，每步 Query 仍要与历史 K 做 Attention；跨所有 Decode 步累计的 Attention 交互计算并不会因此简单变成 O(n)。建议角标写：

> 不缓存时，历史 K/V 投影会被重复计算；这里的 O(n²) 只指这部分重复投影工作，不代表使用 KV Cache 后整个生成过程总计算量降为 O(n)。

### P1-4：S01 的示例回答需要标“教学示意”或给出真实运行证据

**位置：S01（约第 692 行）。**

“KV Cache 是给模型记笔记的本子”是教学类比，适合作为开场，但观众可能以为这是模型真实生成结果。建议在角标标注“示例回答 / 教学示意”，除非真的使用指定模型、Prompt、参数运行并保存结果，才可以标“本项目实测”。

### P1-5：课程覆盖映射要细到“知识点—视频集”，不能只证明文件被列入清单

**位置：§2.26（约第 484–522 行）与附录 A。**

37 个 Markdown 文件计数已经统一，这是进步。但“文件已映射到某一集”不等于“文件中的知识点都被安排讲解”。

特别需要复核 Part I 第 1 章 LLM 入门：原文不仅包括 Token/Embedding/Transformer，还包含 LLM 定义与发展、能力边界、应用、Prompt/RAG/Agent/Harness、位置编码、MHA、Residual/Norm、FFN、现代结构演进等。当前第 1 集脚本只覆盖其中一部分，第 2 集标题又主要是 Tokenizer。

建议建立一张更细的覆盖表：

| 原文章节/小节 | 原文知识点 | 计划集数 | 深度（完整/概览/预告） | 对应讲稿段落 | 对应镜头 | 是否验收 |
|---|---|---|---|---|---|---|

至少把 Part I 第 1 章、Part II 第 3 章概念与代码篇逐项分配，避免出现“文件列进了映射表，但具体知识点没有任何一集讲”的情况。

### P1-6：参考视频发布日期出现内部不一致

**位置：K4（约第 567 行）与 §1.1/附录 B。**

K4 将参考视频的实测数字标为“2025-10”，但方案其他位置记录的观看日期为 2026-11-15，作者主页显示的近期发布时间口径也需要核对。建议回到视频页面或可靠元数据核实发布日期；若无法确认，只标“参考视频实测，观看日期 2026-11-15”，不要猜发布时间。

### P1-7：Remotion 可以作为主管线，但它不是 OSI 开源软件，需先确认授权适用性

**位置：§3.6（约第 798–834 行）。**

Remotion 的当前官方条款将其定义为 source-available、非 OSI 开源软件；个人或最多 3 人团队符合条件时可使用 Free License，其他公司/团队可能需要 Company License。若该课程由企业团队制作，或用于企业内部工作流，需先按实际团队规模和使用场景核对许可证。

建议在制作工具决策表增加：
- Remotion 版本；
- 团队/组织是否符合 Free License；
- 是否需要 Company License；
- 许可证确认日期。

官方说明：
https://www.remotion.dev/docs/license/pricing
https://www.remotion.dev/docs/terms

另外，Remotion + SVG/CSS 更适合做 2.5D 连续舞台、镜头平移缩放和数据驱动动画。若目标是复杂真实 3D 摄影机运动，需要明确是否引入 Three.js/React Three Fiber 或后期合成；不要默认 SVG 的镜头缩放等同于完整 3D 场景。

### P1-8：源码 commit 台账不能长期保留省略号

**位置：附录 B 引用台账（约第 912 行）。**

`1291f317…`、`1d019ce1…` 等省略写法不足以作为正式追溯记录。开拍前应补齐完整 40 位 SHA、对应仓库 URL 和具体文件路径；Datawhale `main` 也要在开拍时锁定 commit。
