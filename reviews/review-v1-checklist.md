# SGLang 动画视频课程方案审核与制作修订清单

## 结论

GLM 返回的《样片制作方案》已经具备完整的前期策划结构：参考视频研究、Datawhale 章节知识映射、第一集解说稿、30 个镜头分镜、素材清单和动画实现建议。方向正确，可以进入样片制作准备。

但它目前是**文案与分镜方案**，不是已验证的动画样片，也不能用文档末尾的自评勾选替代技术审校和成片验收。正式渲染前至少修正以下 P0 项。

## P0：进入动画制作前必须修改

### 1. Temperature 与 Softmax 的先后顺序写反

当前第一集解说稿写成：

> 第一步，Softmax：把每个候选的分数，变成加起来等于 1 的概率。然后，由采样参数决定怎么抽……温度低于 1……

这会让观众理解成先 Softmax、再调整温度。正确的教学链路应为：

> 模型先给出 logits。如果设置了温度 T，就先用 T 缩放 logits，再经过 Softmax，得到概率分布。温度越低，分布通常越尖锐；温度越高，分布通常越平。之后再按 Top-k / Top-p 规则筛选候选、重新归一化，最后进行采样。

建议同步修正 S24 的动画：温度旋钮应先作用于 logits 分数，再显示 Softmax 概率柱；不要让观众看到“先完成概率柱，之后才被温度旋钮改变”。

原教程 Part II 第 3 章明确说明温度先缩放 logits，再 Softmax。参考：
https://github.com/datawhalechina/zero-to-sglang/blob/main/course-material/ch/part2/第3章_前向与生成.md

### 2. KV Cache 单位标注和分镜中的数字要统一

按照方案中的配置：L=36、n_kv=8、d_h=128、bf16（每元素 2 bytes），单个请求每个 token 的 KV Cache 理论增量为：

`2 × 36 × 8 × 128 × 2 = 147,456 bytes`

即：
- 每 token：0.140625 MiB（约 0.147456 MB）
- 100 token：14.0625 MiB（约 14.7456 MB）
- 101 token：约 14.20 MiB
- 100 个输入 token + 200 个输出 token，共 300 token：约 42.19 MiB
- 32K token：4.5 GiB
- 8 个 32K 请求：36 GiB

Datawhale 原文把这些二进制换算结果写作 MB / GB。样片可以尊重原文数字，但建议在专业课件中明确采用 MiB / GiB，或者在角标说明“原文以 MB/GB 表示，数值按 1024 进位计算”。原文链接：
https://github.com/datawhalechina/zero-to-sglang/blob/main/course-material/ch/part1/第4章_推理的核心数据结构入门.md

分镜 S19 当前写“数字滚动到 200 token≈14.2MB”，这是错误的。14.20 对应的是 100 个 Prompt Token 加 1 个 Decode Token（总计 101 token）；若是 100 个输入 + 200 个输出，应该展示总计 300 token、约 42.19 MiB。

建议把 S19 改成两个连续数字：
1. `100 输入 + 1 输出 = 101 token → 约 14.20 MiB`
2. `100 输入 + 200 输出 = 300 token → 约 42.19 MiB`

同时在画面上注明 B=1，且这是理论稠密 KV 占用，不含权重、激活、碎片、对齐和引擎额外开销。

### 3. “每算出一个 Token，就发回一段”与前面的 Detokenizer 讲解矛盾

当前 S25–S26 已经正确说明：一个 token 可能只包含一个 UTF-8 字符的一部分字节，Detokenizer 需要保存状态，确认有安全可显示的文本后才输出。

但 S27 的旁白又写：

> 服务端每算出一个 Token，就真实地发回一段。

这与前文矛盾。应改为：

> 服务端生成新的 Token ID 后，会交给 Detokenizer 增量解码。只有形成安全、可显示的文本增量，才会通过 SSE 推送给浏览器。一次推送可能对应一个或多个 Token，也可能暂时没有可显示的新文本。Token 和 SSE 数据块不是一一对应的。

S27 的动画已经有“事件≠一个 Token”角标，应让旁白与动画表达一致。SSE 数据包可以继续用教学简化格式，但必须标记它不是完整的 OpenAI Chat Completions 线上数据结构。

### 4. TTFT 不能简单说成“主要就是 Prefill 花的时间”

当前旁白将“等第一个字”的时间主要归因于 Prefill。这样容易让学习者把 TTFT 等同于 Prefill latency。

建议改为：

> 从请求发出到客户端收到第一个可用输出片段，这段时间叫 TTFT。它可能包含请求传输、Tokenizer、排队与调度、Prefill、首 Token 采样、Detokenizer 和首段返回等环节。Prefill 通常是重要组成部分，但 TTFT 不等于 Prefill 耗时。

动画可在 TTFT 标尺上分段标出 Queue / Tokenize / Prefill / First token / Return。若为了简化不按比例绘制，注明“流程示意，不按耗时比例”。

### 5. Decode 的显存访问动画不要画成“每一步完整搬运两大包”

当前旁白和 S22 分镜写“每一步都要把模型权重和整段缓存，从显存里读一遍”，并用两捆完整包裹反复进出显存门。

这个画法过于绝对，容易使人误以为每个 Decode iteration 都发生一次“完整 KV Cache 作为单个整体搬运”。建议改成：

> Decode 每一步都需要执行模型各层的计算，访问相应权重；同时，当前 Query 要读取各层历史 K/V，完成 Attention。对小批量 Decode 来说，相对于计算量，权重和 KV 数据访问通常占据更大的成本，因此常表现为显存带宽受限。

画面改成逐层展示：权重数据从 HBM 进入计算单元；当前 Query 访问该层历史 K/V；新 K/V 写回 Cache。旁边用“典型小 Batch 情况”作限定，不要画成整个 KV Cache 每步整体复制。

## P1：建议在锁定整集之前修正

### 6. 第一集信息密度过大，和后续集数有明显重复

当前第一集已经深入讲了：
- Tokenizer、Embedding、Transformer、QKV、Attention、FFN、LM Head
- Prefill、Decode、KV Cache 和显存估算
- Temperature、Top-k、Top-p
- Detokenizer、SSE、取消

但后续第 2、3、4、7、8、9 集又分别要详细讲 Tokenizer、训练/推理、Prefill/Decode、请求链路、KV Cache、HTTP/Streaming。

建议将当前第一集定位为**第 0 集 / 全景导入集**：每个环节只讲“它是什么、在整条链路中处于哪里”，只保留一个核心故事线；公式推导、数据结构、代码实现全部留给后续正式章节。这样既可以保留“按下回车”的吸引力，也不会让后续课程重复播放同一段内容。

另一种办法是把第一集改为纯粹的“一个请求的旅程”，把模型内部机制移到后续章节。两种方式都比现在“第一集讲到很深，后面又重新讲一遍”更清楚。

### 7. 参考视频的风格迁移要保持原创

方案正确地提出不复用参考视频画面、音乐和角色。建议进一步规定：借鉴的是叙事方法和动画语法（连续空间、问题链、逐步构建、镜头推拉、数字徽章），不是照搬其具体场景、吉祥物、道具外形、字体组合、音效素材或镜头编排。

本项目应建立自己的视觉识别：颜色体系、Token 形状、服务器/模型/缓存图标、字体、背景空间和音效语义。可以保留“深色科技感 + 金色强调”的抽象方向，但做原创资产。

### 8. 章节覆盖计数需要统一

文档前面称“33 个教学文件（2+5+15+5+3+3）”，但附录列出的 Part II 文件数量与该计数不一致；附录 A 又称共 37 个 Markdown 文件。建议按实际文件树生成一份机器可核验的清单：路径、Part、章节、概念/代码、计划视频集、是否完成讲稿/分镜。不要只用“已覆盖”总数自证无遗漏。

### 9. “原文实测数字”徽章要谨慎

Qwen3-4B-Thinking-2507 的 KV Cache 数字来自模型配置与公式推算的理论稠密占用，不是实际运行时显存监控结果。画面应标“原文估算 / 理论计算”，不要标“原文实测”。只有真正运行并记录出来的数据才能标“实测”。

同样，参考 B 站视频里的 Qwen3-0.6B 词表数据可以作为“参考视频实测示例”，不能写成 Datawhale 原文数据或本项目实测数据。

### 10. 外部资料引用要精确到可追溯

目前一些章节只写“官方 SGLang 文档”“NVIDIA 白皮书”“教程某节”。正式成片前应维护引用台账：
- 结论 / 数字 / 画面对应的原始论据
- 原始 URL
- Git commit 或文档版本
- 发布/更新时间与访问日期
- 本项目采用的解释是否属于教学推演

第一集尤其应锁定 Datawhale 仓库 commit 和 mini-sglang commit，避免课程更新后章节链接或代码行发生漂移。

### 11. CC BY-NC-SA 4.0 许可边界需要确认

方案自行假设“非商业教学改编”。这不是用户已经确认的前提。若计划用于商业培训、付费课程、带商业赞助或其他商业化发行，需要先确认授权边界或联系权利方取得单独许可。重绘图片并不会自动消除对原教程文字和结构的改编许可要求。

## 动画工程建议

现方案同时提出 After Effects / Fusion、Manim、Remotion、SVG、Canvas、Lottie，多工具并行对于第一支样片可能过重。

建议先建立一个主制作管线：

- 主时间轴与合成：Remotion（React 组件、时间轴、音频、字幕、镜头动画、批量渲染）
- 图形：SVG / Canvas（Token、数据流、缓存格、请求队列、树结构）
- 数学专场：只有在公式、矩阵、几何推导确实需要时才用 Manim 输出透明背景片段
- 最后统一由主时间轴合成 MP4

如果后续需要手工精修，再考虑 After Effects / DaVinci Resolve；第一支样片不要一开始就让四套工具共同承担基础画面。

## 建议的样片生产关卡

不要直接渲染 11 分钟。按以下顺序验收：

1. **风格帧**：先出 3 张 16:9 关键帧（开场、连续舞台、核心技术特写），确认画面美术体系。
2. **30 秒动态样条**：验证镜头推拉、对象逐步构建、字幕、音效和解说同步。
3. **60–90 秒技术证明片段**：建议做 KV Cache 的“重复计算 → K/V 保存 → Decode 复用”连续动画。这段既有清楚的因果，也能检验技术准确性。
4. **整集 Animatic**：先用简化图形、临时配音和占位音效跑通全部时长，检查节奏与重复内容。
5. **锁稿、配音、精动画、混音、字幕、导出**。

正式验收不要只看画面好不好看，要逐项核对：旁白每个技术断言是否正确、画面是否解释了该断言、数据单位是否一致、原文与补充资料是否区分、后续章节是否重复。

## 最终建议

这份 GLM 文档可以作为第一轮导演/编剧稿的基础，不需要推翻重做。下一轮任务应是“按 P0/P1 修订 + 制作 30 秒风格样条 + 60–90 秒 KV Cache 技术样片”，而不是继续扩展交互功能或批量生成全课程。
